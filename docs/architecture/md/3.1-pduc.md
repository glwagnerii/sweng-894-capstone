## 3.1 Partially Dressed Use Cases
Listed below are the system use cases described at a high level.

### **3.1.1 Capture or Open Image**
- **Goal in Context**: An end user wants to capture a new photo or select an existing image for classification.
- **Actors**: End User, Camera, Photo Library, Device Manager, Phone/Computer OS
- **Preconditions**: The app is installed and has permission to access the camera, photo library, and cloud storage.
- **Scenario Steps**:
  1. The user launches the app and selects "Capture" or "Open Image."
  2. If "Capture," the app checks for available camera devices.
  3. If multiple cameras exist, the user selects a device.
  4. The OS prompts for camera permissions if not already granted.
  5. The app displays a live video stream from the selected camera.
  6. The user clicks "Take Photo" to capture an image (pausing the stream).
  7. The user can "Retake" (return to live stream) or "Confirm" the image.
  8. Upon confirmation, the app uses the captured image for inference and displays results.
  9. If "Open Image," the user browses and selects an image from local or cloud storage.
  10. The selected image is used for inference and results are displayed.

```mermaid
sequenceDiagram
    participant EndUser
    participant App
    participant DeviceManager
    participant PhoneOrComputer

    PhotoLibrary-->>App: Return selected image
    App->>AIModel: Run inference
    AIModel-->>App: Return results
    App-->>EndUser: Display results
```

### **3.1.2 Detect and Classify Objects**
- **Goal in Context**: The user wants to analyze an image to detect and classify objects using the active AI model, and review timing statistics for each processing step.
- **Actors**: End User, AI Model, GPU, External API
- **Preconditions**: An image is selected from the library or captured from the camera, and an AI model is available.
- **Scenario Steps**:
  1. The user initiates object detection and classification (capture or select).
  2. The app loads the image and records load time.
  3. The app preprocesses the image and records preprocessing time.
  4. The app runs inference using the AI model (optionally accelerated by GPU) and records inference time.
  5. The app post-processes results and records post-processing time.
  6. The app displays detected objects with bounding boxes, class labels, and timing statistics for each step.
  7. The user reviews the results and timing breakdown. The user may select a class label to query an external app API for matches, which are then displayed in a list.

<div style="display: flex; justify-content: center;"><div style="width:600px">

```mermaid
sequenceDiagram
    participant EndUser
    participant App
    participant AIModel
    participant GPU
    participant ExternalAPI

    EndUser->>App: Initiate object detection
    App->>App: Load image & record load time
    App->>AIModel: Preprocess image & record preprocessing time
    AIModel->>GPU: Accelerate inference (optional)
    GPU-->>AIModel: Return inference results
    AIModel-->>App: Return detected objects & record inference time
    App->>App: Post-process results & record post-processing time
    App-->>EndUser: Display results & timing statistics
    EndUser->>App: Select class label
    App->>ExternalAPI: Query for matches
    ExternalAPI-->>App: Return matches
    App-->>EndUser: Display matches list
```

### **3.1.3 Show Matches for Selected Objects**
- **Goal in Context**: The user wants to see best-fit matches or related content for selected objects.
- **Actors**: End User, External API
- **Preconditions**: Objects have been detected and classified in the image.
- **Scenario Steps**:
  1. The user selects one or more detected objects.
  2. The app queries an external API or local database for matches.
  3. The app displays a list or grid of matches related to the selected objects.
  4. The user selects a match from the list to view details (see 3.1.4).

### **3.1.5 View and Manage History**
- **Goal in Context**: The user wants to review, sort, filter, view details, or delete previous classification results.
- **Actors**: End User, Store, External API
- **Preconditions**: The app has stored classification history.
- **Scenario Steps**:
  1. The user navigates to the history view.
  2. The app displays a list of past classification results from the store.
  3. The user sorts history by name or date.
  4. The user applies filters to the history list.
  5. The user selects an item to view details (details are retrieved via API).
  6. The user deletes items from history.
  7. The app updates the history accordingly.

### **3.1.6 Manage Models (via Settings)**
- **Goal in Context**: The user or developer wants to install, update, configure, select, or remove classification models through the Settings interface.
- **Actors**: End User, Developer, Model Manager
- **Preconditions**: The app supports model management in Settings and has access to model sources (local/cloud).
- **Scenario Steps**:
  1. The user/developer opens the Settings interface.
  2. The user adds a new ONNX model from local or cloud storage.
  3. The app validates the model and returns input/output shape and file size.
  4. The user edits display name, description, confidence threshold, and IOU threshold.
  5. The user selects a model from the list of previously added models.
  6. The user updates or deletes models from the list.
  7. The app validates and applies model changes.

### **3.1.8 Integrate with External Apps**
- **Goal in Context**: The app supports integration with external APIs to retrieve matches and detailed information for classified objects.
- **Actors**: End User, External API
- **Preconditions**: Integration settings are configured and supported APIs are available.
- **Scenario Steps**:
  1. The app calls the external API for matches, providing one or more class labels as input.
  2. The API returns a list of matched items, each containing a thumbnail image, name, optional description, categories, and other metadata.
  3. The user selects a matched item.
  4. The app calls the external API for details, providing the matched item's ID.
  5. The API returns detailed information, such as instruction steps, a list of ingredients, links to videos (e.g., YouTube), and additional metadata for filtering.

### **3.1.14 Handle Invalid Models or Images**
- **Goal in Context**: The user wants the app to detect and handle errors related to invalid, unsupported, or duplicate models when adding from the Settings screen.
- **Actors**: End User, Model Manager
- **Preconditions**: The user is trying to add a model from the Settings screen.
- **Scenario Steps**:
  1. The user attempts to add a new ONNX model from the Settings screen.
  2. The app checks for duplicate models and does not allow duplicates.
  3. The app validates that the model is an ONNX model in YOLO format (input shape 1,3,640,640) and includes label names in its metadata.
  4. If the model is invalid or duplicate, the app displays an error message and does not add the model.
  5. If the model is valid, the app adds it to the model list and automatically selects it.

```mermaid
sequenceDiagram
    participant EndUser
    participant App
    participant ModelManager

    EndUser->>App: Add ONNX model (Settings)
    App->>ModelManager: Validate model (duplicate, format, input shape, metadata)
    ModelManager-->>App: Return validation result
    App-->>EndUser: Display error (if invalid/duplicate)
    App-->>EndUser: Add to model list and select (if valid)
```
